## 2. Cómo funciona cada forma de pago

### A) Tienda online → solo Mercado Pago (Payment Brick)

El comprador **no elige efectivo/transferencia** en la web. Solo MP:

```
Carrito → datos personales → envío (Correo/pickup) → Payment Brick
  → POST /payments/brick-init  (orden PENDING + descuenta stock + preference)
  → Usuario paga en el Brick
  → POST /payments/brick       (tarjeta / ticket / account_money / wallet)
  → Webhook MP → actualiza estado real
  → /checkout/success consulta GET /payments/order-status/:id
```

| Método en el Brick | Qué hace el backend | Estado típico | Qué ve el comprador |
|--------------------|---------------------|---------------|---------------------|
| Tarjeta crédito/débito/prepaga | `/v1/payments` con token; `binary_mode: true` | `PAID` o rechazo inmediato | Success o toast error |
| Ticket (Rapipago / Pago Fácil, etc.) | Crea pago offline | `PENDING` + `ticketUrl` | Success “pendiente” + link comprobante |
| Dinero en cuenta (`account_money`) | Pago wallet | `PAID` o `PENDING` | Success según status |
| Wallet purchase | No cobra en brick; espera webhook | `PENDING` hasta webhook | Success pendiente → luego PAID |

**Protecciones profesionales ya implementadas:**

- Monto recalculado en servidor (no confía en el cliente).
- Re-cotiza envío Correo al pagar; si cambió > $0,50 → cancela orden y pide re-cotizar.
- Stock con `SELECT FOR UPDATE` / restore si falla o expira.
- Tope de órdenes PENDING por email.
- Webhook: HMAC + timestamp + dedupe (`WebhookLog`).
- Cleanup automático de carritos abandonados / PENDING viejos.
- Override manual en BO no lo pisa el webhook.

**Tests automatizados:** 45 unit tests de payments pasan.

### B) Efectivo y transferencia → solo backoffice (para la hermana)

```
Backoffice → Órdenes → “Registrar venta”
  → Canal: Tienda / IG / WhatsApp / Feria / Online
  → Pago: CASH | TRANSFER | MERCADOPAGO
  → POST /orders (requiere ADMIN)
  → Orden creada + stock descontado
```

| Caso | Cómo se registra | Cómo “confirma” el cobro | Qué ve la hermana |
|------|------------------|---------------------------|-------------------|
| Efectivo (feria, local) | Modal crear orden + CASH | Ya es venta cobrada; puede poner estado PAID/manual | Lista en **Órdenes** con canal y notas |
| Transferencia | Modal + TRANSFER | Marca estado manualmente cuando ve el depósito | Igual; usar **notas** (“comprobante CBU…”) |
| Link MP social | Pantalla **Pagos** | **PAUSADA** — API no tiene `/payment-links` | Mensaje amber “módulo pausado” |

**Importante:** efectivo/transferencia **no pasan por Mercado Pago**. Son registro operativo + stock. La hermana es la que valida el dinero.

## 4. Correo Argentino — flujo y riesgos

```
Checkout: CP + items → POST /shipping/rates → tarifas D/S
Opcional: GET /shipping/agencies?provinceCode=
Al pagar: backend re-cotiza si provider = correo_argentino
Post-venta (admin): POST /shipping/import/:orderId → MiCorreo
Admin: carga tracking manual desde panel MiCorreo
```

| Requisito | Si falta |
|-----------|----------|
| Credenciales `CA_*` + `CA_ENVIRONMENT=PROD` | Cotización falla → fallback WhatsApp |
| `weight` en variantes (gramos) | Peso mal calculado → tarifa incorrecta |
| Perfil remitente / `CA_SENDER_*` | Import falla con errores de emisor |
| Orden con dirección estructurada | Import incompleto |

**Estado del código:** bien pensado (cotización pública, import admin, re-cotiza al cobrar).  
**Estado operativo:** depende 100% de config PROD y datos de producto (peso).

## 9. Respuesta directa a tus preguntas

**¿La implementación de Mercado Pago está correcta y profesional?**  
Sí, para un e-commerce LATAM de este tamaño está **por encima del promedio**: Brick unificado, webhook firmado, stock, montos server-side, re-cotización de envío, auditoría de estados. Unit tests de pagos en verde (45).

**¿Efectivo y transferencia?**  
No en la tienda pública. Sí en el **panel de tu hermana** al registrar ventas de feria/IG/WhatsApp. Ella ve la orden con método y canal; el cobro lo confirma ella (no MP).

**¿Cómo le llegan los datos a su dashboard?**  
Consulta la API con sesión admin. Órdenes y métricas se leen de la misma Postgres. **No le “llegan” proactivamente** (sin email/push).

**¿Correo Argentino?**  
Diseño correcto. En prod debe cotizar si `CA_*` están bien y los productos tienen **peso**. Import/tracking es flujo admin post-venta.

**¿Hay huecos / 500 / 404?**  
No hay un desastre de endpoints rotos en el core. El hueco grande de producto es **notificaciones** y el módulo de **payment links** (conscientemente pausado). Errores de red se manejan con toasts/pending conservador; conviene Sentry para 5xx reales en prod.
